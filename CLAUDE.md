# CLAUDE.md

aninames builds a multilingual alias index for anime (and visual novel) titles and characters: any title or character name typed in Japanese (kanji, kana), romaji with any spelling, English, Korean or Chinese should find the right work or character. It ships data files, not a server.

## Commands

All dev commands are mise tasks; package.json has no scripts. The toolchain is bun 1.3.

- `mise run fetch [source…]` — download raw data into `.cache/raw/<source>/`
- `mise run stage [source…]` — parse raw data into `.cache/stage/<source>.jsonl`
- `mise run build` — merge the staged sources into one SQLite file per layer in `dist/`
- `mise run search <query>` / `mise run eval` — query the built layers / run the golden queries in `tests/golden.ts` and the ttheme cast in `tests/ttheme.tsv` (`ANINAMES_LAYERS=core` limits the layers, `ANINAMES_MISSES=1` lists misses)
- `mise run pack` — zstd-compress the built files into `dist/release`; `bun src/cli.ts unpack` turns the `.sqlite.zst` files there back into `dist/*.sqlite`, which the weekly workflow does with the latest data release when a source does not load, so the static site still deploys and the run still fails
- `mise run chunk [bytes]` — cut each layer's search keys and entity rows into sorted gzip'd JSON files of about 32 KB in `dist/site` (the static index served at `names.ttheme.dev`): `<layer>/<table>/<hash>.json.gz`, `manifest.json`, `CNAME`, `NOTICE.md`, `index.html`
- `mise run compare [per band]` — search the probe sample with SQLite and with the client (`src/client/`) over `dist/site`; prints first % per form and rounds, files and KB per cold query, and fails when the files find fewer entities first than SQLite
- `mise run lib` — compile the client into `lib/` (JavaScript and `.d.ts`) for the npm package
- `mise run probe [size]` — search a frozen sample (`tests/probe.json`, made on first run; delete it to draw a new one) of works and characters in three popularity bands by forms of their own names (Japanese, kana, romaji, swapped, short vowels, one-letter typo, Korean, Korean initials, Korean typed on an English keyboard) and Korean Wikipedia spellings with the `kowiki` layer held out; reports first %, MRR and query counts, names several entities share apart
- `mise run silver` — hide the external ids that join characters across sources, attach them to Bangumi by name alone, and report pairwise recall and precision against them
- `mise run han` — rebuild `src/han.txt` from Unicode's Unihan and OpenCC's shinjitai table
- `mise run ci` — lint + typecheck (the client also alone, against Node's types) + tests

## Pipeline

- A source (`src/sources/<name>.ts`, default export of type `Source` from `src/model.ts`) has a `fetch` that downloads into its raw dir and a `stage` that yields `Entry` records. `src/sources/index.ts` lists the names and loads them lazily.
- An `Entry` is one work or character as one source sees it: `id` (a `Ref`, `<namespace>:<id>`), `kind`, `refs` (ids in other namespaces the source says are the same thing), `names` (text, BCP 47 `lang` when known — `ja`, `ja-Latn` for romaji, `en`, `ko`, `zh-Hans`, `zh-Hant`, `zh` — and a `NameKind`), `works` (a character's works, as refs), `roles` (a character's role in each of them, `lead`, `support` or `minor`, where the source says: Bangumi and VNDB), `link` (name texts to attach by when there are no refs), `rank` (the source's own popularity number, higher is more popular), `type`, `year`, `origin` (a work's countries of origin, Wikidata P495 as ISO 3166-1 alpha-2 codes), and, from Bangumi only, `within` (the works above it: its parent story, series or main version, and the work whose side story, volume, DLC or other version it is), `related` (its sequels and prequels, summaries, full stories, alternative versions and the adaptations that share its title) and `near` (character appearances, same and other settings, spin-offs and adaptations under another title: evidence for grouping only, never `related`). `attach: true` means the entry only adds names to an entity found through its refs or link and never creates one; such an entry may omit `kind`. `family: true` (Danbooru's copyright tags) means it names a whole family of works.
- A redirect to a section of an article (`kind: 'section'`, Korean Wikipedia's 페른 → 장송의 프리렌#페른) usually names a character or a part of the work, not the work itself, and ranks well below a real alias.
- Korean Wikipedia articles also yield cast lists (`src/sources/cast.ts`: the 일본어 표기 template, definition lists and bold names with a Japanese name in parentheses); a pair attaches to the one character of that name in the article's work family.
- Readings (`kind: 'reading'`, kana) are what Korean names are generated from at build time (`hangulVariants` in `src/text.ts`); a source never generates names itself.
- Bangumi is the spine: only its entries make entities, so an entity's id is its Bangumi id (`w/bangumi:<id>`, `c/bangumi:<id>`) and never moves, and only its data gives structure: a work's `within` and `related`, a character's works and roles, popularity and the adult flag. It takes anime, book series (manga, light novels) and games (a game only with a cast, a VNDB link or 100 favorites), and characters of role person or mecha. Every other source only attaches names, ids and tags to a Bangumi entity (`src/spine.ts`), and an entry that reaches none is dropped. It attaches through its refs, chained through any source but never joining two Bangumi entries; else a work by a Japanese title only one Bangumi work of that medium (a VN counts as a game) and year (±1) has, when no other work of its own source near that year shares it; else a character by its names, the most specific first (a Japanese name with kanji or a separator, a long kana name, a two-word Latin name, a short kana name, one word): among the Bangumi characters in the works its own works and Danbooru qualifiers (its aliases' too) reach within two hops of `within`, `related` and `near`, or, when it reaches none, among all of them. A name matches when only one Bangumi character carries it, or when all who do are in one family (Bangumi's own duplicates; the most collected wins); at the most specific level any name matches, a name that matches several is no evidence and names that match different characters are a conflict unless those are in one family. A character whose works are known but none is in Bangumi never matches Bangumi-wide unless a Danbooru tag is among its entries, and a Danbooru tag without a qualifier, which Danbooru keeps for a name one character has, also takes a Bangumi namesake with ten times the collects of the next.
- A family entry goes to every work its evidence ties together: the works carrying its id (Wikidata P13236) and the works sharing one of its titles (a Japanese one, or a Latin one, the tag's own name included, matched by `titleKey`, which keeps long vowels and Roman numerals apart; a qualifier comes off unless another copyright tag has the same name without it), grouped by Bangumi's `within` and `related` and a shared character (one in more than 200 works does not count). It takes the groups with an anchor, else the one group holding a work its own name finds, else the one group, else a group of two or more holding most of the works and larger than any other, else none. Only the family's head (the anchor, else the earliest work) takes its names; the rest take the tag alone. For homes only, the tag also reaches every work those works tie to through `within` and `related`, one level up.
- Every title and name key folds Han variants, simplified, traditional and Japanese, into one character (`src/han.txt`).
- A character's home (`src/homes.ts`) comes from the tags its Bangumi works reach: a work's own tags, then those of the works above it (`within`, `src/graph.ts`) and the copyright tags spread to it, one level up per step. The home is the most specific tag that a majority of its works reach, weighted by role (lead 3, support 2, minor 1, unknown 2), among tags with at least 0.8 of the character's own Danbooru posts (on ttheme's commons the right home always has more); else the copyright tag its own tag's qualifier names (a copyright with no qualifier or `(series)`); else the tag the most of its works reach (one big enough first, then more posts); else what most characters sharing its qualifier chose. Only `unlicensed` carries homes. A home's cast puts its leads first, then its supporting cast, by the roles of the works the tag reaches, then the rest; a lead counts only in a work with at least a third of the collections of the most collected work the tag reaches, so a spin-off's or a minor film's lead is supporting. The client's `cast` gives each its `role`.
- Popularity is Bangumi's count (a work's collections, a character's collects) on a log scale against its 99th percentile (a count of zero is no evidence, not a low score); other sources' counts do not rank. Danbooru posts only order `tagged` and `cast`.
- Each layer marks, per entity and language, its best name with that name's rank among every layer's best (`names.pref`, 0 is the best of all): main and official names before synonyms, short names, readings, redirects, sections and generated names, then the names more sources give, then the source (Wikidata, AniDB, VNDB, anime-offline-database, Bangumi, kowiki, Anissia, Danbooru). A client takes the lowest it has per language; the label walks `ja`, `en`, `ja-Latn`, `ko`. Names keep their source's word order: `en` names often put the given name first, `ja-Latn` romaji (VNDB, Bangumi, readings) usually the family name.
- `within`, `basis` and `related` together tie works into families: a query matching a franchise also lifts the anime in its family whose own names contain the query, and family members share popularity.
- Bangumi's `nsfw` marks a work adult; a character is adult when all its Bangumi works are. Search returns them flagged and filters them only on request.

## Layers and licenses

Every source belongs to one layer, and a built file never mixes layers: share-alike licenses cannot be merged into one database. The search library joins the layers on the user's machine.

Derived scores (popularity, standing, flags) are the only cross-layer values a file carries, never names.

- `core` — CC0 and ODbL: Wikidata, anime-offline-database (cedya77's continuation), VNDB. The built `core.sqlite` is ODbL.
- `kowiki` — CC BY-SA 4.0: Korean Wikipedia article titles and redirects.
- `unlicensed` — sources that state no license or whose data comes from sites that state none: Bangumi (the spine), AniDB titles, Anissia, Danbooru. Required: `core` and `kowiki` only attach to its entities, so neither works without it.
- Namuwiki is not used (CC BY-NC-SA, robots.txt forbids it). AniList and TMDB terms forbid storing their data; pixiv forbids crawlers. None of them is a source: their ids on a work come from Wikidata and anime-offline-database.

## Conventions

- First-party code carries no comments.
- Single quotes, no semicolons, 2-space indent, 120 columns (biome). ES modules, `.ts` import extensions.
- Network: every request sends `USER_AGENT` from `src/net.ts`; be polite (Danbooru about 1 request/s sustained, Zerochan 60/min, Wikidata SPARQL one query at a time, AniDB never directly — use the Anime-Lists mirror). Downloads go through `download` (writes `.part`, then renames).
- Errors thrown for the user start with `aninames:`.
- The client (`src/client/`, the npm package) runs unchanged on Node 22 and Bun: no `bun:*` and no Bun globals, and it imports only `es-hangul` and the pure `src/text.ts`, `src/model.ts` and `src/match.ts`. What it reads from the files is `unknown` until checked.
- No backwards-compat shims or legacy fallbacks.
